## batchSize 扫描 (N=10M, tasks=2816)

活跃核数 ≤ `ceil(taskCount / batchSize)`,故 batchSize 越大、参与计算的核越少。

| batchSize | 活跃核数 | scan (ms) | 有效带宽 (GB/s) |
|---|---|---|---|
| 1 | 2816 | 18.927 | 16.9 |
| 2 | 1408 | 14.674 | 21.8 |
| 3 | 939 | 13.348 | 24.0 |
| 4 | 704 | 12.548 | 25.5 |
| 8 | 352 | 11.691 | 27.4 |
| **16(默认)** | **176** | **11.602** | **27.6** |
| 24 | 118 | 12.129 | 26.4 |
| 32 | 88 | 12.957 | 24.7 |
| 48 | 59 | 18.309 | 17.5 |
| 64 | 44 | 24.046 | 13.3 |

**最优 batchSize = 16(176 核)**。曲线两侧都上扬,是真正的谷底而非扫描边界。
重跑复现良好(18.927 vs 18.940、11.602 vs 11.616,变异 ≈0.1%)。

**这是与参考项目相反的结论,值得单独记录。** DRAN(fp16 点积)的最优在 b=3~4
(约 700~900 核);本负载最优只用 **176 核**,用满 2816 核反而慢 **63%**。
原因:Hamming 扫描的算术强度极低(每 32 B 只做 4 次 XOR+POPCOUNT),瓶颈在
DRAM 带宽而非算力,增核只增加调度开销与缓存争用。**同一块卡、不同负载,
最优并行度相差约 4 倍** —— 不能沿用别的负载的调参结论。

## 三组对比(k=500,同机同日)

延迟为**稳态**口径:数据已驻留卡上,不含一次性 fill / flushHostCache / preloadMemory。

> **⚠ 读这张表前必读。** A 组有两个实现,结论完全相反:
> 单线程 numpy 会让设备看起来快 40 倍,那是**测量假象**,不是结果。
> 论文中只能引用多线程 C 基线那一列。

| N | 方法 | 每查询延迟 | 链路流量 / 查询 |
|---|---|---|---|
| 1M | A-numpy(单线程,**不可用于结论**) | 29.972 ms | 32 MB 需入主机 |
| 1M | **A-C/OpenMP(384 线程)** | **3.188 ms** | 32 MB 需入主机 |
| 1M | B 设备扫 + host 选 | **1.335 ms** | 4.0 MB |
| 1M | C 全下沉 | 14.131 ms | 2.0 KB |
| 10M | A-numpy(单线程,**不可用于结论**) | 365.041 ms | 320 MB 需入主机 |
| 10M | **A-C/OpenMP(384 线程)** | **5.460 ms** | 320 MB 需入主机 |
| 10M | B 设备扫 + host 选 | 15.440 ms | 40 MB |
| 10M | C 全下沉 | 50.492 ms | 2.0 KB |
| 100M | A-numpy(单线程,**不可用于结论**) | 4175.605 ms | 3.2 GB 需入主机 |
| 100M | **A-C/OpenMP(384 线程)** | **62.299 ms** | 3.2 GB 需入主机 |
| 100M | B 设备扫 + host 选 | 153.905 ms | 400 MB |
| 100M | C 全下沉 | **102.936 ms** | **2.0 KB** |

B 的延迟 = 扫描 + 结果回传 flush(1M: 0.897+0.438;10M: 11.531+3.909;
100M: 114.884+39.021)。C 的延迟 = 扫描 + merge。

**四组都是精确 Hamming,recall 恒等** —— 性能对比中质量是常量,不存在
"降质换速度"。100M 的 B、C 与主机 C 基线均已对 numpy 参照验证,三者
第k名距离一致(93)、返回距离范围一致([84,93])。

### ★ 主结论:设备在单查询延迟上打不过认真实现的主机

| N | C ÷ A(多线程主机) | B ÷ A |
|---|---|---|
| 1M | 慢 4.4× | **快 2.4×** |
| 10M | 慢 9.2× | 慢 2.8× |
| 100M | 慢 1.65× | 慢 2.5× |

**之前记录的 40.6× 是单线程基线造出来的假象。** 换成 OpenMP 多线程 C 实现后,
主机快了 **67 倍**(4175.6 → 62.3 ms),设备的优势全部消失。

唯一的例外是 **N=1M 时 B 快 2.4×**,但那是因为主机在小规模上被开销主导
(384 线程启停 + 0.93 ms 的固定 merge),不是设备的真实优势。

### ★ 计算资源对照(N=100M)—— co-design 的核心证据

比"谁快"更重要的是**各自动用了什么样、多少个计算单元**:

| | 计算单元 | 数量 | 占可用比例 | 需要 FPU | 用到向量引擎 | 扫描吞吐 | **每单元吞吐** |
|---|---|---|---|---|---|---|---|
| **A** | x86 硬件线程 | **384** | 100% | 有(闲置) | 见下方待确认 | 51.8 GB/s | 0.135 GB/s |
| **B** | MU 核(扫描) | **176** | 6.2% | **无** | **未用** | 27.9 GB/s | 0.158 GB/s |
| **C** | MU 核(扫描) | **176** | 6.2% | **无** | **未用** | 35.3 GB/s | **0.201 GB/s** |
| **C** | MU 核(merge) | **1** | 0.04% | **无** | **未用** | — | — |

三条读法:

1. **设备只动用了 6.2% 的核**(2816 个里的 176 个),就做到了 384 线程 Xeon 的
   1/1.65。剩下 93.8% 的核在这个负载上是**加了会更慢**的(见 batchSize 扫描)。
2. **单个 MU 核的吞吐是单个主机线程的 1.49 倍**(0.201 vs 0.135 GB/s)。
   一个连 FPU 都没有的 RISC-V 标量核,单位吞吐胜过一个乱序 x86 线程 ——
   因为它紧挨着自己的内存,不与另外 383 个线程抢共享带宽。
3. **全程没碰浮点单元,也没碰 FP16/FP32 向量引擎。** kernel 里只有
   `__builtin_popcountll`,纯标量整数。这是本项目最直接的 co-design 论据:
   **这个检索原语不需要任何浮点或向量硬件。**

**为什么这比 wall-clock 更重要。** 浮点向量的 ANN 检索需要 FPU、每 doc 读
2 KB —— 这两条决定了它**不可能下沉到内存侧**。二值签名的 Hamming 检索只需
XOR + POPCOUNT、每 doc 读 32 B、每查询只回传 k 个 id ——
**四个条件同时满足,才谈得上"放进内存"**。本实验用 MX1P 作为载体,
证明的是这条可行性,而不是"这块卡比 Xeon 快"。

> 待补充的两项(会影响对照的严格性):
> - 主机 384 是**硬件线程**数;物理核数未记录(若为 192 核 ×2 SMT,
>   则每物理核 0.270 GB/s,反超 MU 核)。需 `lscpu` 补齐。
> - 主机侧是否被 gcc 自动向量化成 AVX-512 `VPOPCNTDQ` 未确认。
>   若是,则对照更有说服力:**主机需要 SIMD 才能达到该吞吐,设备用标量就够**。

### 设备 ≈ 多少个主机线程?(N=100M 线程扫描)

| threads | 延迟 | 等效带宽 |
|---|---|---|
| 1 | 267.179 ms | 12.0 GB/s |
| 2 | 140.777 ms | 22.7 GB/s |
| 4 | 202.719 ms | 15.8 GB/s ← 反常,疑 NUMA 放置 |
| 8 | 112.511 ms | 28.4 GB/s |
| 16 | 72.958 ms | 43.9 GB/s |
| 32 | 56.146 ms | 57.0 GB/s |
| 64 | 54.502 ms | 58.7 GB/s |
| **128** | **52.591 ms** | **60.8 GB/s**(主机最优) |
| 256 | 55.122 ms | 58.1 GB/s |
| 384 | 54.972 ms | 58.2 GB/s |

设备 C 的 102.936 ms 落在 t=8(112.5)与 t=16(73.0)之间,按吞吐插值:

> **一块 MX1P ≈ 9~10 个主机线程**(该机 384 线程可用)。

主机在 **32 线程左右饱和于 ~60 GB/s**,再加线程无收益 —— 这是内存墙。
设备峰值 35.3 GB/s,也是内存墙,只是位置更低。**两边撞的是同一堵墙,
高度差约 1.7 倍** —— 这是"近内存不赢在算得快"的双向证据。

### ★ 交叉点:on-card selection 只在规模足够大时才划算

| N | C ÷ B | 结论 |
|---|---|---|
| 1M | 10.6× | B 明显更快 |
| 10M | 3.3× | B 更快 |
| 100M | **0.67×** | **C 更快 1.5×** |

C 在 10M 与 100M 之间反超。两个机制同时起作用:

1. **C 的固定开销被摊薄。** merge 的直方图归并是 2816×257 = 723,712 次单线程
   累加,**与 N 无关**。实测:100M 时候选几乎为零,merge = 12.402 ms;
   1M 时 merge = 13.006 ms —— 两者几乎相同,直接证明这是一个恒定地板。
2. **B 的回传成本随 N 线性增长。** 100M 时要把 400 MB 距离经链路搬回主机,
   仅 flush 就 39.0 ms,且这部分无法通过优化设备侧消除。

### merge 耗时拆解(C 模式)

| N | scan | merge | 候选数(重试后) | merge 占比 |
|---|---|---|---|---|
| 1M | 1.079 ms | 13.006 ms | ~118K | 92% |
| 10M | 10.564 ms | 39.928 ms | ~1.17M | 79% |
| 100M | 90.530 ms | 12.402 ms | ~0(阈值收紧至 93) | 12% |

**merge ≈ 直方图归并(恒定 ≈12.4 ms)+ 候选扫描(正比于候选数)。**
非单调是因为 100M 触发了溢出重试,阈值从 118 收紧到 93,候选数骤降。

### 扫描带宽

| N | B 扫描 | C 扫描 |
|---|---|---|
| 1M | 35.7 GB/s | 29.7 GB/s |
| 10M | 27.8 GB/s | 30.3 GB/s |
| 100M | 27.9 GB/s | **35.3 GB/s** |

100M 时 **C 的扫描比 B 快 21%**(90.5 vs 114.9 ms):B 需把 4 亿个 int32
距离物化到设备内存(额外 400 MB 写),C 只写直方图与少量候选。

峰值 35.3 GB/s = 268 GB/s 的 **13.2%**。参考:DRAN 项目在同一块卡上达到
30.1 GB/s(11.2%)—— 两个算术强度迥异的负载撞在同一个带宽区间,提示瓶颈
不在 kernel 内层而在访存路径本身。

## 正确性验证(全部在最大规模上通过)

| 验证项 | 规模 | 结果 |
|---|---|---|
| B 模式距离 vs numpy | N=10,000 | `PASS: 10000 个距离逐位一致` |
| B 模式距离 vs numpy | **N=100,000,000** | `PASS: 100000000 个距离逐位一致` |
| C 模式 top-k | N=10,000 | `PASS`,第k名=109,重合 96/100(其余为并列) |
| C 模式 top-k | **N=100,000,000** | `PASS: 500 个 id 唯一且距离全部 <= 第k名(93)`,返回距离范围 [84, 93] |
| 强制溢出 + 自愈 | N=10,000, t=2 | `nCand=400 overflow=1` → 收集不足(67/100) → 收紧至 109 → `PASS` |

**溢出自愈路径在硬件上按设计工作,且与本地 Python 模型的预测逐个数字吻合**
(模型预测:候选 400、overflow=1、先 67/100、收敛 exactThresh=109、终 100/100)。

大规模验证用 `verify_large.py`(分块 + `bitwise_count`,峰值内存 ≈100 MB,
与设备同用 257 桶计数排序求第 k 名)。该工具已确认能**拒绝**三种设备真实可能
产生的坏输出:距离超标、重复 id、哨兵填充(均 exit 1)。

## 诚实边界

- **单线程 numpy 基线已被多线程 C 基线取代 —— 前者不得用于任何结论。**
  `np.bitwise_count` 与 `argpartition` 都是单线程 ufunc,拿它对比 176 个
  设备核会得出 40.6× 这种失真结论。补测的 OpenMP C 基线快 **67 倍**
  (4175.6 → 62.3 ms),设备优势随之全部消失。numpy 那几行仅作为
  "为什么必须做这个对照"的记录保留。
- **10M 那一行对主机有缓存红利。** 320 MB 大概率仍在该机的 L3 内:主机扫描
  在 10M 时达 82.3 GB/s,而 100M 时只有 51.8 GB/s。**100M 才是真正的
  DRAM-vs-DRAM 对比**,小规模行不应单独引用。
- **t=4 的 202.7 ms 反常**(慢于 t=2)疑为 NUMA 放置问题,未进一步定位。
  不影响饱和点与交叉点的结论,但若要在论文中给出完整曲线,应先用
  `numactl` 复测该点。
- **延迟为稳态口径**:数据已在卡上。100M 的一次性装载约 3.8 s 单列于上。
- **合成随机签名。** Hamming 距离与内容无关,故延迟测量无偏;但真实语料的
  距离分布会改变候选数,进而改变 merge 的可变部分与溢出重试行为。
- **C 的 100M 计时不含重试成本。** 阈值在 warmup 期间已收敛到 93,5 次计时
  均在收敛后进行。生产中可缓存该阈值,故此口径合理,但需明写。
- **粗阈值默认 118 对大 N 偏松**,100M 时触发溢出并重试一次。按数据规模预设
  阈值可避免,属可调参数而非缺陷。
- **近内存不赢在算得快 —— 这次是被自己的数据证实的,不是引用来的。**
  优势只能建立在三点上,而它们都**尚未测量**:
  1. **容量**:卡上 DAX 有 1863 GB,该机主机内存 128 GB。数据集超过主机内存后,
     A 组必须从存储流式读,那才是设备的主场。本实验最大只到 3.2 GB,
     **完全落在主机内存内 —— 即在最不利于设备的区间里做的对比**。
  2. **并发**:每个主机查询都要让 3.2 GB 过一遍内存;设备把这部分完全卸载。
     多路并发下扩展性可能完全不同,但本实验是**单查询**口径,测不出来。
  3. **链路流量**:C 每查询过 2 KB(压缩比约 160 万倍),而 A 要求整库常驻
     主机内存。这是唯一已被本实验直接测到的设备优势。
- **未测多查询批处理。** 单查询口径;批处理会摊薄 merge 的固定开销,可能使
  交叉点大幅左移。

## 论文应当怎么写(基于以上数据)

**不能写**:"近内存 Hamming 扫描比主机快 N 倍"。在 3.2 GB 这个规模上它慢 1.65×,
而且这个规模完全装得进主机内存 —— 是设备最不占优的区间。

**可以写,且有数据支撑**:

1. **一块 MX1P ≈ 9~10 个主机线程**(384 线程机器上的实测交叉点),同时把
   每查询链路流量从"整库 3.2 GB 需常驻主机"降到 **2 KB**。
2. **on-card selection 存在规模交叉点**:相对 host-side selection(B),C 在
   10M 与 100M 之间反超(50.5 vs 15.4 → 102.9 vs 153.9),原因已定量拆解为
   "C 的固定 merge 地板 12.4 ms 被摊薄"与"B 的回传随 N 线性增长"。
   **这一条不依赖主机基线,是设备内部两种设计的干净对比,最稳。**
3. **主机与设备撞的是同一堵内存墙**,高度差约 1.7 倍(60 vs 35 GB/s),
   双向证据支持"瓶颈在访存而非算力"。
4. **最优并行度与负载强相关**:本负载最优 176 核,用满 2816 核慢 63%;
   同卡上 DRAN 的浮点负载最优在 700~900 核。

**要让"更快"这个论断成立,必须补的实验**(按性价比排序):
- **超出主机内存的规模**(如 20~100 GB 签名库)。这是设备唯一可能真正取胜的
  区间,也是 CXL 大容量卡的立论基础。当前 3.2 GB 的实验完全没有触及。
- **多路并发吞吐**(而非单查询延迟):设备卸载后主机 CPU 空出来的价值。
- **能耗**:每查询焦耳数,近内存的经典论点,本实验完全未测。

## 明确的优化方向

**merge 的直方图归并是当前唯一的结构性瓶颈**:723,712 次累加、单 task、
跨 2816 个分散的 1028 B 区域,几乎每次访问都 cache miss(12.4 ms / 723,712
≈ 17 ns 每次,与 DRAM 延迟量级一致)。做成树形并行归约可将这 12.4 ms 压到
接近零,进而:

- 1M 的 C 从 14.1 ms 降至 ~1.7 ms(优于 B 的 1.3 ms 仍有差距,但差距从 10.6× 缩到 1.3×)
- 交叉点从 ~50M 大幅左移
- 100M 的 C 从 102.9 ms 降至 ~90.5 ms,即逼近纯扫描成本

这也与参考项目的结论一致:DRAN 的单 task merge 占其总时间 13%,同样被标记为
首要优化点。本负载扫描更便宜,故同一瓶颈被放大到 79~92%。
